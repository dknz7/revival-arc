# Vivarc rules: spaces and windows

**Status: APPROVED by Byron, 2026-11-06 (decisions in Part 3). Built 2026-11-07.** Every rule in Part 2 has unit tests (`tests/test_space_rules.py`) and a live check in a sandbox Vivaldi (`tools/sandbox-rules.mjs`, one PASS/FAIL line per rule). Byron added `Move to <Space>` (under "Tabs") on 2026-11-07. On 2026-11-08 he approved the split-space exception to invariant 4 (a plain click gathers a split space) and had Vivarc's own drag restamp removed (decision 4). His Dia sidebar button of the same day is not a spaces rule, so it is in `docs/HOW-IT-WORKS.md`, though the same script checks it. So are the Dia row's Shield, Copy link and Translate icons and the private-window behaviour (Task 8v, 2026-11-12: `D.row-icons`, `D.shield-panel*`, `D.private-window-*`, `D.fullscreen-row`). A change to these rules is a change to this file first.

**Why this exists.** A run of bugs (a space click that does nothing, links filed into the wrong space, a space that "moved on its own") all came from the same place. Vivaldi's own record of which space a window shows can disagree with what the window is actually showing. Vivaldi and Vivarc then each act on a different idea of where things are. Part 1 is how Vivaldi really behaves, as measured. Part 2 is the rules Vivarc promises, including where it deliberately overrides Vivaldi.

**Terms used below**
- **Space:** a Vivaldi workspace. A tab's space is `workspaceId` in its `vivExtData`. A tab with no key is in the **default** space.
- **Record:** Vivaldi's own map of which space is active in which window (`getActiveWorkspaces()`; per window, `getActiveWorkspaceId(windowId)`). A window with no entry is on its default space.
- **Parked:** a tab whose space is not the space its window shows. It is hidden from the sidebar but still open.
- **Lives in:** the window that holds a space's tabs.

## Part 1: how Vivaldi 8.2 behaves (measured)

Measured on 2026-11-06 in a sandbox Vivaldi 8.2.4133.96 with Vivarc loaded, each case run 3 times, in both the Dia and Arc layouts. Vivaldi's own behaviour was identical in both layouts; the only differences came from Vivarc's command bar. Case IDs refer to the spike logs.

### Switching: `setActiveWorkspace(window W, space X)`
| X is... | Result |
|---|---|
| already active in W | Nothing moves. W gets focus. (A1) |
| active in another window O | Nothing moves. **O** gets focus. Same whichever window's UI makes the call. (A2, A9c) |
| parked in W | W's record becomes X and X's most recent tab is activated. Nothing moves. (A3) |
| parked in O, whatever O shows | **All** of X's tabs move from O into W at the start of the tab strip, W's record becomes X, and W does **not** get focus. (A4, A5, A10) |
| split across W and O | All of X's tabs end up in W. The tab activated comes from the **first-created** window holding X; recency across windows is ignored. (A6, A6b, A6c) |
| empty (no tabs) | A start page tagged X is created and activated. (A7) |
| the default space (`undefined`) | W's record entry is removed and W's default tab is activated. If W has no default tab, a default start page is created. (A8a, A8b) |

### Changing the active tab without a switch
- Activating a tab of another space (`chrome.tabs.update(id, {active})`) **does not change the record**. The window then shows a tab of one space while recorded as another. (G1–G3)
- Changing the *active* tab's space **is** a switch: the record follows. If that space is active in another window, the record does not change and **focus jumps to that window**. (G4, G6)
- Changing an *inactive* tab's space does nothing to the record. (G5)

### New tabs
- **Every new tab goes into the window's recorded space**, stamped by Vivaldi at creation. This holds for `chrome.tabs.create` with no space, inactive tabs, tabs with an opener, and Vivaldi's own New Tab command. (B1, B1i, B2, B3c)
- **The opener is ignored:** a link opened from a tab of another space still goes into the recorded space. (B2b)
- **The record wins over what is shown:** a window recorded as X but showing a Y tab puts its new tab in X. (B7c)
- A tab created with an explicit space Y and `active: true` switches the window's record to Y. (B2c) *Not reproduced on re-test (2026-11-07, the sandbox checks for the repairs): such a tab left the record where it was, so setups that need the record switched now switch it explicitly.*
- Creating a tab in a window focuses that window. (B5)
- A tab created within about 0 ms of a switch is a race, with mixed outcomes. At 100 ms it reliably lands in the new space. (B4)

### Moving tabs between windows (`chrome.tabs.move`)
- A moved tab keeps its space and arrives parked. The target window's record does not change. (C1, C2, C4)
- Moving a space's only tab out of a window leaves that window recorded as the space while showing a default tab. No start page is created. (C3)

### Closing
- Closing a space's last tab with `tabs.remove` leaves the window recorded as that space while showing a default tab. Ctrl+W instead creates a start page tagged with the space. (D1, D1k)
- **Closing a window:**
  - Every named-space tab in it **moves to the most recently focused other window**, at the start of the tab strip, before the window closes. Default-space tabs close with the window. (D2–D7)
  - Spaces that were active in the closed window lose their record entry, so they arrive **parked**, even in a window showing another space. (D2c)
  - The rehoming follows focus history, not where the space lives, so it can **split a space** across windows. (D8)
- Quitting by closing windows one at a time rehomes everything into the last window, so only that window comes back. **File → Exit** keeps every window. (E3)

### Restart
- On startup each window's record is rebuilt from its active tab, and the **first-created** window wins when two windows' active tabs share a space. **Startup also pulls** that space's parked tabs from other windows into the winner. (E1, E2, E2b)

### Deleting a space (`removeWorkspace`)
- All of its tabs close, in every window. The calling window switches to default first. (F1)
- If the space was active in another window, that window **stays recorded on the deleted space**. (F2)
- **A window that held only that space's tabs closes.** (F3)

### Not Vivarc's business, but worth knowing
- Vivaldi's exit confirmation dialog, on by default, blocks quitting until it's answered.
- In 3 of 49 runs, tabs created in the last second or so before an immediate exit were lost on restart. None were lost with a 5 s pause.

## Part 2: the rules Vivarc keeps

### Invariants: true whenever no gesture is in progress
1. **One truth.** Which space a window shows is Vivaldi's record and nothing else. Vivarc reads the record and does not infer it from the active tab. The one exception is a Vivaldi whose record can't be read at all: the sidebar (its tiles and pins included) and the command bar then fall back to the active tab's space, while the repairs do nothing (they log one warning), since without the record they would be guessing.
2. **Record and screen agree.** A window's active tab always belongs to the space its record names (default when there is no entry). When something breaks that, Vivarc repairs it (see "Repairs").
3. **A space lives in one window.** All of a space's tabs are in one window. Vivaldi 8.2 can split a space (a window close, a moved tab), and Vivarc repairs it (see "Repairs"). Vivaldi 8.3 keeps a space in one window by itself (measured, task 8t: a move into a space with tabs in another window is refused, "ambiguous windowId", and `chrome.tabs.move` leaves a hidden space's tab where it is), so a split cannot be built there; the split rules below (the split row of the gesture table, the split exception to invariant 4, repair 3) are **8.2 only**, kept as a safety net for a session an 8.2 left split, and the sandbox cases that build a split report SKIP on 8.3.
4. **A plain click never moves tabs between windows.** Moving tabs is always explicit: shift+click, ctrl+shift+click, or dragging. The one exception: a plain click on a space split across windows gathers it into the window it lives in, as repair 3 would (see the gesture table). Approved by Byron, 2026-11-08.
5. **Vivarc does not stamp spaces.** New tabs get the recorded space from Vivaldi (B1). Vivarc sets a tab's space only when it deliberately puts a tab into one, all through one call (`native.setSpace`, `08-space-native.js`):
   - a favorite or pin whose tab is in another space or window, brought here (into the space on screen);
   - a tab torn off into a new window (its default space), and the tear-off's Undo (back into its old space and window);
   - a tab dropped into another window's sidebar (the space that window shows);
   - `Move to <Space>` (on 8.3; on 8.2 it is Vivaldi's own `moveToWorkspace`);
   - Clean Up's restore of a cleaned tab (into the space it was cleaned from);
   - a tab picked whose space no longer exists (into the space on screen in the window it was picked in; see "A tab picked in the command bar");
   - repair 0, the one repair that sets a space: a tab whose space no longer exists, into its window's default space;
   - a Peek preview made into a tab (Open in New Tab, Open in Background): its preloaded tab, into the space on screen beside the tab the link was in (`17-peek.js`);
   - undelete (Task 9c): a tab of the space brought back, into that space, in the window it comes back to (a Recently Closed restore brings it back with the space's id; a tab opened anew by its address is put there; see "Deleting a space");
   - the blank tab of a space whose last tab closed, only if Vivaldi did not file it in that space itself (it does, B1; see "Closing a space's last tab").

   How: on **Vivaldi 8.2** a write of `workspaceId` to the tab's `vivExtData` (`chrome.tabs.update` merges `vivExtData`, so leaving the key out would keep the old space; the default space is written as `workspaceId: 0`, and Vivaldi drops the key when it is 0), with `chrome.tabs.move` first for another window. **Vivaldi 8.3** owns that key: a `workspaceId` written to `vivExtData` is dropped while the other keys still merge, so the space is set with Vivaldi's own tab move, `tabsPrivate.move({ tabIds, target, windowId, workspaceId })` (what its Move to Workspace and tab drop use), always with the window: onto the tab itself, or before the tab at the index asked for. Which Vivaldi it is comes from the move's own argument check, asked once with an empty move (`native.movesByTab`), not from a version number. Either way the tab is read back, and the call throws when the tab is not in that space and window. Its old new-tab stamping is removed: it was redundant, and it undid switches (A8b).
6. **Every window shows a space that exists and has a tab.** A record pointing at a deleted space, or at a space with no tab in that window, is repaired.

### Gestures on a space tile (named space X)
| X is... | Click | Shift+click | Ctrl+shift+click (Mac: cmd+shift) |
|---|---|---|---|
| shown in this window | nothing | nothing | move X to a new window |
| shown in another window | go to that window | bring X here | move X to a new window |
| parked in this window | show X here | show X here | move X to a new window |
| parked in another window | **go there: that window shows X and comes to the front** | bring X here | move X to a new window |
| split across windows | treated as living in the window it is shown in, otherwise the one with most of its tabs; shift+click and the move both gather every tab, and so does a plain click, into the window it lives in (as repair 3 would; the one exception to invariant 4, approved by Byron, 2026-11-08) | | |
| empty | show X here (Vivaldi makes a start page) | same as click | move X to a new window (opens with a start page) |

The default space can't be moved, because it belongs to each window. Clicking it shows this window's own default tabs.

**Dots.** A tile gets a dot when its space **lives in another window**, shown or parked there. The tooltip says what each click does.

### Tabs
- **`Move to <Space>`** (a tab's right-click menu) moves the tab into that space with Vivaldi's own move, as its keyboard shortcut does. The window stays on the space it shows (if the tab is the one on screen, another tab of the space takes the screen first, or a blank tab if there is none). If that space is shown in another window, the tab goes to that window. A space that is parked in another window: on **Vivaldi 8.3** the tab goes to that window and joins the space there, which stays parked (that window keeps showing what it shows; measured, task 8y exp2), and a toast says it moved to another window (Task 9a). On **Vivaldi 8.2** it cannot be reached (Vivaldi's move fails from here, and into that window it lands in the space shown there): the menu says so ("Z is parked in another window. Show it there first, then move the tab.") and nothing moves. A space with no tabs anywhere takes the tab in this window. If Vivaldi's move does not put the tab in that space and window, the menu says so and Vivarc undoes its own steps (the tab goes back on screen if it was, and a blank tab it opened closes). It does not undo Vivaldi's move: a tab Vivaldi put somewhere else stays there, and a space that leaves split is gathered by repair 3.
- **A tab picked in the command bar** (which lists every tab of the window, parked ones too) is shown with its space: a tab parked in this window's other space switches the window to that space first (A3), then is activated. A tab whose space is shown in another window (a split space's stray) goes to that window, as a tile click does, and repair 3 gathers it. Without the record or the switch, the tab is just activated. The same pick shows a tab chosen from the New Tab dropdown (Open Tabs, Recently Closed) and from Recently Cleaned.
- **A tab whose space no longer exists is never switched to** (Task 9a). Vivaldi 8.3 restores a closed tab of a deleted space with the deleted space's id (its own bug, task 8y), and its switch takes any id: the window would show a space no tile can reach, and every new tab there would be filed under it. So a picked tab whose space is not in Vivaldi's list is moved into the space on screen **in the window it was picked in** (Byron, 2026-11-14: a restored tab comes to the window you clicked in, not to its old window) and activated there; if it was on screen in another window, that window's most recent tab of its own space takes the screen first. While the list can't be read, a tab of a named space is only activated, never switched to. The command bar still lists such a tab, but never ranks its Switch to Tab first and never autocompletes its address.
- **New tabs** (Ctrl+T, + New Tab, palette pages, links) go into the window's recorded space (Vivaldi's own behaviour). Given invariant 2, that is always the space on screen.
- **New-tab position:** a new tab from Ctrl+T, + New Tab or the palette goes to the top of its space's list. A link opens next to the page it came from.
- **Favorites and pinned tabs** open in this window and **in the space on screen**. Activating a tab parked in another space breaks invariant 2 (G1–G3), so Vivarc never does it. A favorite's or pin's tab that is in another space or window is brought here and put into the space on screen before it is activated, so no second tab opens.
- **Dragging a tab into another window:** the tab joins the space that window shows. This is the explicit "move this tab" gesture. Vivaldi's own drop (a tab dragged between tab strips) puts the tab into the space the target window shows (H2), and Vivarc's sidebar does the same (Byron, 2026-11-08): a tab row dragged into another window's sidebar moves into that window at the drop position (above or below the row by the nearer edge, so no folder is made across windows; the New Tab row puts it last), into the space that window shows, and is activated there. It is the same write as a tear-off: out of its split view (its peers in the source window leave it too) and its folder. The source window keeps its space; if that was the space's last tab there, repair 1 handles it. The move runs under the repair busy mark, and a failure toasts and leaves the tab where it was. A drag that only claims to be a sidebar's tab (the drag type put on by a web page or another app) is refused: the drop is taken only with the one-time pass a real sidebar drag leaves on the background page (Task 8w). A drag inside one window is unchanged. The target accepts the drop (`dropEffect` move), so the source's tear-off stays quiet, and the tear-off also checks the tab is still in its window. A tab moved by other code (`chrome.tabs.move`) keeps its space and arrives parked (C1); the repairs take it from there.
- **Dragging a tab out of the sidebar beyond the window** (a tab row only: not a pin, favorite or folder, and not the window's only tab) opens it in a new window, in that window's default space (Byron, 2026-11-08); the source window keeps showing its space. The tab leaves its space on purpose: a space lives in one window, so a tab that kept a space still shown in the source window would be gathered straight back by repair 3. A deliberate move into the default space, so it is written with `workspaceId: 0` (invariant 5). Order: the window is created first (the tab moves into it), and only then is the tab restamped, because while it is still the source window's active tab, changing its space is a switch there (G4). The repair busy mark is held for the whole gesture. If the tab was its space's last one in the source window, that window is left recorded on a space with no tab and repair 1 switches it to default (C3/D1). If the window is made but the restamp fails, the tab stays in its old space in the new window, repair 3 gathers it home, and one `[vivarc]` warning is logged. The same write takes the tab out of its split view (`tiling`) and its folder (`group`), and its split-view peers in the source window lose their tiling too, as Close Split View does (a key leaves `vivExtData` only when written as null: omitted, undefined and "" keep it, measured). A drop onto another window's page (not a Vivarc drop target) tears off as well, since the browser reports it the same way as a drop on nothing. Escape does not cancel a drag that has left the window (the browser's drag loop takes the key, and a cancelled drag ends like a drop), so every tear-off shows "Opened in a new window" with **Undo** for 5 s, in the new window: Undo moves the tab back to its index in the window it came from, restores its original space (`workspaceId` as it was) and activates it again if it was active, under the same busy mark; the emptied window closes itself (measured). Undo does not restore a split view or a folder.

### Repairs: when Vivaldi breaks an invariant
Vivarc checks after the events that can break an invariant (tab activated, tab moved or attached, tab closed, window closed, space deleted, startup, and a tab created in a space that no longer exists), waits for the browser to settle, then repairs in this order. **Repairs never change a tab's space, except a tab whose space no longer exists, which repairs move to its window's default space** (rule 0; amended by Byron, 2026-11-14). Why: Vivaldi 8.3 brings a deleted space's tabs back with the dead id (from Recently Closed, with its own Reopen Closed Tab, and in the session after a restart), where no tile can ever show them; and before Task 9a, Vivarc's own pick then switched the window into the dead space. No other repair can reach those tabs, and nothing else ever would, so without this they stay unreachable for good (task 8y: Byron's own profile). The default space is the one space every window has.
0. **A tab in a space that no longer exists** (task 8y): it moves to its window's default space, where it is (same window, same place), through `native.setSpace`. Only the leader does it, inside the same debounced pass, at most 25 tabs a pass, each logged. It acts only on a list it can trust: two reads about 1 s apart of Vivaldi's list (the pref) and of its own store, every read non-empty, the two agreeing and unchanged between the reads. At start-up Vivaldi's store is empty until its list has loaded, so nothing moves then. A space undelete can still bring back (its entry in Vivarc's `deletedSpaces` store: the last 10 spaces Vivarc deleted, for 30 days; Task 9c) is left alone, so its tabs come back with it; once its entry expires, is pushed out by the cap or is restored, normal rules apply, and a store that cannot be read heals nothing that pass. When the tab moved is on screen in a window recorded on the deleted space, the record follows it to the default space (measured), so rule 1 has nothing left to do there.
1. **Record points at a deleted space, or the window holds no tab of its space** (F2, C3, D1): switch that window to default. Not when the window's own tab on screen closed and it was its space's last page: the window stays in that space, empty (see "Closing a space's last tab"; it runs under the busy mark, so this rule never sees the moment the space has no tab). A tab moved out of the window (a tear-off, a drop into another window, `chrome.tabs.move`) still leaves it to this rule.
2. **The active tab is in a different space from the record** (G1–G3): activate the window's most recent tab of the recorded space. If there is none, switch the record to the active tab's space, unless that space is shown in another window (G6), in which case switch to default. A window already on default is never switched to default, because that would only steal focus (A8c). Repair 3 gathers the stray tab, and the next pass settles the window. A window is never switched into a space that is not in Vivaldi's list (a deleted one: Chromium puts a dead tab on screen when the window's last default tab closes, task 8y), nor into a named space while the list can't be read: rule 0 takes such a tab home.
3. **A space is split across windows** (D8, after a window close or a tab move): gather its tabs into the window where it is shown. If it is shown nowhere, gather them into the window that holds most of its tabs. Gathering uses `chrome.tabs.move`, so the moved tabs keep their space (C1). Vivaldi's switch can't gather here: it does nothing for a space already shown in the target window (A1). A deleted space is not gathered: rule 0 sends each of its tabs to its own window's default space.
4. **A window close leaves rehomed tabs parked** (D2): no change. They stay where Vivaldi put them, now in one window by repair 3, and a click on the space goes there.

### Closing a space's last tab
(Byron, 2026-11-14, decision 5: the upstream and Arc behaviour, KASOGIT/vivarc#118 and #119; it reverses his earlier decline of #75.) When the tab on screen closes (a page, not a blank tab) and its window holds no other page of that space, the window **stays in that space, empty, with the command bar open** on the space's blank tab. Vivaldi files a new tab in the window's recorded space (B1), so the blank tab is Vivarc's `chrome.tabs.create`, with no space written; a blank tab the space already had (Vivaldi's own Ctrl+W may make one) is shown instead; were the record to have moved off the space, Vivaldi's switch into the empty space makes the start page (A7). The bar keeps that tab, as on landing in an empty space, so **Escape** closes the bar and the window stays in the empty space until you switch. It runs under the repair busy mark; after it, the window is recorded on the space and shows its blank tab, which no repair changes (rule 1 sees a tab of the space, rule 2 a record and screen that agree). The default space behaves the same. Not for: a window that closes with the tab, a deleted space (rule 1), a tab moved out of the window (repair 1, as before), a blank tab closing (the bar's own Escape on a new tab), or a close under another gesture's busy mark (deleting or moving a space). Before, repair 1 switched the window to its default space.

### Deleting a space
The confirmation says how many tabs will close and in how many windows, and that the space can be brought back from the New Tab menu's **Recently Deleted Spaces** (Task 9c). Before Vivaldi deletes it, Vivarc stores what the space was under `deletedSpaces` and reads it back; if the store does not take it, nothing is deleted. If Vivaldi's delete then fails, the menu says so ("Could not delete the space") and the entry just written is forgotten while the space still exists. **Not from a private window:** it shares the profile's spaces but has a store and a view of the tabs of its own, so an undo entry made there would miss the normal windows' tabs and vanish with the window; a private window's tile right-click, its **+** and its Recently Deleted Spaces only point to a normal window (fix round 1 of the review). It keeps the space's id, name, icon, emoji, place in the list, link-routing rules (Vivaldi's delete removes them) and where it lived, its theme, and its tabs in order (address, title, icon, folder, split, pin, mute, and each one's Recently Closed entry, noted right after the delete); its start pages are not kept. The last 10 spaces are kept, each for 30 days. Undelete re-creates the space with **its old id** through Vivaldi's own store (every tab still carrying the id is the space's again), puts back its place, rules and theme, then its tabs in their old order: a tab already back with the id (Vivaldi's own Reopen Closed Tab brings them back under it) is used as it is, never opened twice; the others each from Recently Closed while it is still listed for the same address (with its history; entry ids start afresh after a restart, so they are matched by address and title then), else opened anew by its address and put into the space (invariant 5). They come back in the window it lived in while that is open (in the same browser run), else in the window asking. Vivaldi restores a tab into a window of its choosing when its old window is gone (measured on 8.3: a folder's tabs into a new window of their own; after a restart, the last focused window), so before any tab goes in, every tab of the space already back in another window (a reopened one, after a restart) is taken out of the space there, and so is a tab restored elsewhere, (with that window's own tab put on screen first, if it was on screen) and then into the space in the target window, since 8.3 refuses to split a space; a window a Recently Closed restore made that is left with only blank tabs closes (never one the user opened meanwhile). A pinned tab is pinned again. Then the space is shown there (that window comes to the front). Folders come back last: Vivaldi 8.3 drops a `group` written into a tab's data and also clears a restored tab's old folder, and its first switch into the restored space undid a folder made before it (measured), so once the space is shown each folder is made again with Vivaldi's own move (named as before), checked a second later and remade if it is gone (at most 3 times). Then its entry goes. While the entry stands, the heal leaves the space's tabs alone (repair 0). After the delete, any window still recorded on it is switched to default (F2). If a window holds nothing but that space, the confirmation says the window will close too (F3). A space shown in **another** window is switched off there first (Task 9a): Vivaldi's delete switches only the window it is given, so that window is the one given, and Vivaldi switches it to its default space before it closes the space's tabs. Before, that window stayed recorded on the deleted id for about 0.5 s (task 8y), and a tab made there meanwhile was filed under it. A window holding nothing but that space is not switched (it closes with the tabs). The window the delete was asked in keeps the focus.

### Editing a space
(Task 9c; upstream KASOGIT/vivarc#126, accepted upstream, not built there.) A space tile's right-click menu: **Rename…** (in a field over the space bar), **Change Icon…** (Vivaldi's own 20 workspace icons, or an emoji; an icon clears the emoji), **Move Left** and **Move Right** (Vivaldi's order, which Cmd+Option+Left/Right follow), then **Delete Space…** (the confirmation above). The space bar's **+** makes a space at once, named "New Space" (or "New Space 2"...) with Vivaldi's default icon, and opens its rename; it does not switch to it. Every change is Vivaldi's own workspace manager's call (`setName`, `setIcon`, `setEmoji`, `setOrder`, `addWorkspace`), found like the delete; Vivaldi's store writes the pref. **Rename renames the space's Pinned bookmark folder first** (keeping an `Arc - ` prefix), then the space, so its pins stay with it (if Vivaldi does not take the new name, the folder gets its old name back); while it runs, no window makes the space a new empty folder for a name that does not match yet. A name another space has, the default space's Pinned folder's, or that of a Pinned folder no space claims (a deleted space's, kept for undelete) is refused: two folders of one name would leave the pins to chance. Themes stay keyed by the space's id, so they follow a rename.

## Part 3: decisions (Byron, 2026-11-06)
1. **A plain click on a space parked in another window: go there.** That window switches to the space and comes to the front. (Not chosen: Vivaldi's native "pull it here".)
2. **A window closes with spaces in it:** accept Vivaldi's rehoming to the last-focused window, then gather split spaces (repair 3). (Not chosen: routing each space to the window where it is shown.)
3. **Favorites and pinned tabs open in the space on screen, Favorites included.**
4. **Dragging a tab to another window** puts it into that window's shown space, rather than keeping its own space and arriving parked. Vivaldi's own drop delivers this for a drag between tab strips (H2), and Vivarc's sidebar does the same for a tab dragged into another window's sidebar (Part 2, Tabs). Vivarc had a restamp of its own for tabs moved any other way; Byron had it removed on 2026-11-08, because Vivaldi's drop already does the job and the restamp's one real risk was re-filing a heavy closing window's rehomed tabs (a 100-tab close took 2.5-2.9 s against its 1.5 s re-check).
5. **Closing a space's last tab** (Byron, 2026-11-14) stays in that space, empty, with the command bar open, as upstream and Arc do; this reverses his earlier decline of #75 (Part 2, "Closing a space's last tab").

## Confirmed in the sandbox (H1–H3)
The spike left these unmeasured. They were measured on 2026-11-06, before the build, in the sandbox (`tools/sandbox.ps1`: Vivaldi 8.2.4133.96 with this branch's Vivarc, Arc layout), 3 runs per case, all 3 identical. W shows X (`X1` active, `X2`) with `Y1` parked in W, unless a case says otherwise.
- **H1. Vivaldi's own tab bar, window panel and space switcher.** None of them leaves the record and the screen disagreeing.
  - Tab bar (H1-strip): Vivaldi's strip lists only the tabs of the window's recorded space (`X1`, `X2`), so a parked tab can't be clicked there. A control click on `X2` activated it and left the record on X.
  - Window panel (H1-panel): a single click on `Y1` (under Workspaces > Y) only selects the row. A double click calls Vivaldi's `setActiveWorkspace(W, Y)`: the record becomes Y and `Y1` is active (a switch, not G1).
  - Space switcher (H1-menu, the Workspaces button popup): choosing Y calls `setActiveWorkspace(W, Y)`, with the same result.
- **H2. Dropping a tab into another window.** A real drag is a native OS drag (`tabsPrivate.startDrag`), which CDP can't drive. The case runs the call Vivaldi's drop handler makes in the target window, `PageActions.moveDroppedTabs(O, [X2], X2, -1)`, which moves the tab with `workspaceId` set to **O's recorded space**. `X2` lands at the end of O's strip and becomes active there. It **joins the space O shows**: Z when O shows Z (H2-named), and the default space, with no `workspaceId` key, when O is on default (H2-default). Neither record changes. Vivarc made no calls in this case. So Vivaldi's own drop files the tab into O's shown space (Vivarc's sidebar drop is its own code and writes the same result); `chrome.tabs.move` keeps the space and parks the tab (C1).
- **H3. Favorites and pinned tabs whose tab is in another space.** Vivarc never activated the parked tab (no G1 drift), and the record stayed Y in every run.
  - A pin of X, opened while W showed X (tab bound in X), then W switched to Y (H3-pin): the sidebar shows Y's Pinned folder, so X's pin isn't on screen and can't be clicked.
  - A favorite opened in X, then W switched to Y (H3-fav): clicking it opens a **new** tab bound to the same favorite. Vivaldi puts it in Y and it is active. The X tab stays bound in X, so the favorite now has a tab in each space.
  - A pin of Y whose tab was moved to X (restamped while inactive, G5) (H3-pinmoved): same as H3-fav. A new tab opens in Y and the X tab stays.
